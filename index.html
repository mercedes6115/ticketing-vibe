병목을 기능이 아니라 구간별 경쟁 문제로 나눠 해결한 티켓팅 시스템

이 페이지는 "티켓 예매 서비스를 만들었다"는 소개보다, 예매 오픈 시점에 실제로 어느 구간이 병목이 되었고 그 병목을 어떤 구조로 줄였는지 설명하는 문서입니다. 핵심은 하나의 기술로 모든 문제를 해결한 것이 아니라, 진입 폭주, 좌석 경합, 확정 처리 지연, 실패 복구를 서로 다른 문제로 보고 각각 다른 방식으로 다뤘다는 점입니다.

Summary

이 페이지가 전달하려는 내용

티켓팅 시스템의 어려움은 "예매 기능 구현"이 아니라 "같은 시간에 몰리는 요청이 어떤 순서로 어떤 자원을 압박하는가"에 있습니다. 이 프로젝트는 그 압박을 네 구간으로 나눴습니다. 진입 병목은 대기열로, 좌석 경쟁은 분산 락과 상태 전이로, 확정 처리 지연은 비동기 메시징으로, 실패 후 잔존 상태는 TTL과 복구 흐름으로 다뤘습니다.

Bottlenecks

어디가 병목이었고, 어떻게 줄였나

01

진입 병목

예매 오픈 직후 요청이 좌석 선택과 예약 확정 단계까지 한꺼번에 들어오면서 뒤 단계 전체가 동시에 압박받았습니다.

개선: Redis Sorted Set으로 순번을 관리하고, SSE로 현재 상태를 전파해 좌석 단계로 진입하는 양을 먼저 제한했습니다.

왜 이 방식인가: 이 문제는 쓰기보다 순번 계산과 빠른 읽기가 많았습니다. Sorted Set은 score 기반 정렬 구조라 전체 순서 유지와 특정 사용자의 위치 계산이 모두 빠르고, 서버에서 클라이언트로의 단방향 알림에는 SSE가 가장 단순했습니다.

02

좌석 경쟁 병목

같은 좌석에 대해 거의 동시에 요청이 들어오면서, 단순 조회 후 업데이트 방식으로는 중복 점유를 막기 어려웠습니다.

개선: Redisson 분산 락으로 임계 구간을 보호하고, 좌석 상태를 AVAILABLE → HOLD → SOLD로 전이시켜 경쟁 시점을 아주 짧게 묶었습니다.

왜 이 방식인가: 좌석 문제의 본질은 조회 성능이 아니라 상태 전이의 원자성이었습니다. 인메모리 락은 인스턴스가 늘어날수록 안전하지 않기 때문에, Redis 기반 분산 락으로 상태 변경 직전 구간만 잠그는 방식을 선택했습니다.

03

확정 처리 병목

예약 확정과 후속 처리를 요청-응답 경로에 모두 넣으면 사용자가 기다리는 시간이 길어지고, 하나의 지연이 전체 응답 지연으로 전파됐습니다.

개선: Kafka producer는 요청을 빠르게 수신하고, consumer가 자체 속도로 확정 작업을 처리하게 해 사용자 응답과 내부 처리량을 분리했습니다.

왜 이 방식인가: 중요한 것은 즉시 완료보다 응답 경로를 가볍게 만드는 것이었습니다. Kafka는 생산과 소비의 시간 차를 허용하므로, 요청 급증 시에도 프론트 응답과 백엔드 처리량을 같은 속도로 맞출 필요가 없다는 장점이 있었습니다.

04

실패 후 잔존 상태 병목

사용자 이탈이나 중간 실패 이후에도 좌석 hold나 입장 상태가 오래 남으면 실제 좌석 회전율이 떨어졌습니다.

개선: hold를 영구 상태가 아닌 TTL 기반 임시 상태로 보고, 만료 시 자동 해제되도록 복구 흐름을 설계했습니다.

왜 이 방식인가: 이 문제에서 더 중요한 것은 "빨리 잡는 것"보다 "잘못 잡힌 상태를 오래 남기지 않는 것"이었습니다. 그래서 정상 성공 흐름보다 실패한 흐름의 자동 복구가 설계의 중심이 됐습니다.

Architecture

구조를 나눈 기준은 기술이 아니라 시간 특성이었다

많이 읽히는 문제

대기열은 진입과 순번 확인이 반복되는 구조라, 빠른 읽기와 순서 보존이 중요했습니다. 여기서는 강한 트랜잭션보다 정렬과 빠른 조회가 핵심이라 Redis가 적합했습니다.

아주 짧게 잠가야 하는 문제

좌석 경쟁 구간은 길게 잠그면 전체 처리량이 떨어지고, 잠그지 않으면 중복 점유가 발생합니다. 그래서 "상태를 바꾸는 직전만 잠근다"는 원칙으로 경쟁 범위를 최소화했습니다.

응답과 완료를 분리해야 하는 문제

예약 확정은 사용자 클릭 순간에 전부 끝낼 필요가 없다고 봤습니다. 프론트는 빠르게 응답받고, 백엔드는 독립적인 소비 속도로 확정을 마무리하는 구조가 더 안정적이었습니다.

실패를 자동으로 지워야 하는 문제

실패한 흐름이 좌석과 토큰을 오래 점유하면 시스템은 기능적으로는 살아 있어도 사용자 입장에서는 막혀 있는 것처럼 보입니다. 그래서 복구는 운영 보완이 아니라 핵심 설계 요소로 다뤘습니다.

Validation

무엇이 실제로 개선됐는가

이 프로젝트의 목표는 기능 동작 여부보다, 경쟁 상황에서도 상태가 무너지지 않는지 확인하는 것이었습니다. 따라서 수집한 수치는 단순한 성능 자랑이 아니라, 각 설계 선택이 실제로 어느 병목을 줄였는지 해석하기 위한 근거로 사용했습니다.

해석

가장 중요한 변화는 단일 수치가 아니라 병목을 분리해 볼 수 있게 됐다는 점입니다. 대기열은 진입 폭주를 줄였고, 분산 락은 좌석 경쟁 구간을 보호했으며, Kafka는 응답 경로와 확정 경로를 분리했습니다. 그 결과 사용자가 체감하는 흐름과 백엔드 내부 처리 흐름을 별도로 해석할 수 있는 구조가 생겼습니다.

Trade-offs

이 설계가 남긴 비용과 다음 과제

빠른 응답과 즉시 완료는 같이 가지 않았다

Kafka로 확정 경로를 분리하면서 사용자 응답은 가벼워졌지만, 최종 완료 시점은 소비 지연에 영향을 받게 됐습니다. 즉, 즉시 완료성보다 응답 경로 안정성을 우선한 선택이었습니다.

기술을 분리할수록 운영 복잡도는 올라갔다

Redis, Kafka, SSE, WebSocket을 함께 쓰면 각 계층의 책임은 명확해지지만, 장애 전파 경로와 관측 포인트는 오히려 더 많아집니다. 구조적 분리는 성능 향상과 맞바꾼 운영 비용이기도 했습니다.

보상 트랜잭션과 멱등성은 아직 더 정교해져야 한다

현재 결제는 mock 기준입니다. 실제 운영 수준으로 가려면 PG 연동, 멱등성 키, 재처리 전략, "일부 성공 후 후속 실패" 같은 케이스를 어떻게 되돌릴지까지 더 명시적으로 설계해야 합니다.

티켓팅 기능 자체보다, 병목을 구간별 문제로 분리하고 줄이는 과정을 설명하는 문서
