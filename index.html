동시성 문제를 분리해서 다루는 티켓팅 시스템 만들기

티켓팅 시스템은 단순한 예매 기능 구현보다, 예매 오픈 순간에 몰리는 요청을 어떻게 제어할지에서 난도가 갈립니다. 이 프로젝트에서는 동시 접속, 좌석 경합, 예약 확정 지연을 하나의 문제로 다루지 않고 대기열, 좌석 선점, 비동기 확정 흐름으로 나눠 각각에 맞는 방식으로 설계하고 검증했습니다. 핵심은 기술을 많이 붙이는 것이 아니라, 각 단계에서 실제로 어떤 경쟁과 병목이 발생하는지 구분하고 그 성질에 맞는 저장 구조와 동기화 전략을 선택하는 것이었습니다.

Problem

어떤 문제를 풀고 싶었나

이 프로젝트에서 다루고 싶었던 문제는 "예매가 된다"가 아니라 "몰릴 때도 버틸 수 있는가"였습니다. 일반적인 CRUD 기반 예매 서비스는 단건 요청 처리에는 문제가 없어 보이지만, 예매 시작 시점처럼 많은 사용자가 한 번에 몰리는 상황에서는 전혀 다른 문제가 드러납니다. 이때 중요한 것은 요청 수가 많다는 사실 자체보다, 같은 자원에 대한 경쟁이 매우 짧은 시간 안에 겹치고, 일부 실패가 전체 상태를 오래 오염시킬 수 있다는 점이었습니다.

동시에 들어오는 요청

예매 오픈 직후 다수 사용자가 한 번에 진입하므로, 좌석 화면에 바로 보내기 전에 진입량을 제어할 대기열이 필요했습니다. 문제는 단순히 요청 수가 많은 것이 아니라, 좌석 선택과 확정 같은 비싼 작업 앞단에 무제한 진입이 생긴다는 점이었습니다.

같은 좌석에 대한 경합

여러 사용자가 같은 좌석을 거의 동시에 선택할 수 있기 때문에, 최종적으로 한 명만 점유되도록 보장해야 했습니다. 이 구간은 조회 성능보다 상태 전이의 원자성이 더 중요했고, 누가 먼저 클릭했는가보다 최종적으로 중복 예약이 남지 않는가가 핵심이었습니다.

무거운 예약 확정

예약 확정과 결제 처리를 요청-응답 경로 안에서 모두 끝내면 응답이 느려지고, 한 단계의 지연이 전체 흐름으로 번집니다. 특히 확정 처리 특성상 DB 변경, 후속 메시지, 상태 전파가 겹치기 때문에 사용자 체감 응답과 최종 일관성을 같은 경로에서 동시에 만족시키기 어려웠습니다.

만료와 실패의 복구

좌석 hold 만료, 사용자 이탈, 중간 실패 같은 경계 조건까지 포함해 상태를 어떻게 되돌릴지 함께 설계해야 했습니다. 성공 흐름보다 더 어려운 것은 실패한 흐름이 좌석과 토큰을 오래 점유하지 않게 만드는 것이었습니다.

Strategy

문제를 한 번에 풀지 않기로 했다

대기 진입, 좌석 선택, 예약 확정을 한 요청 안에서 모두 처리하면 구현은 단순해 보이지만 실제로는 가장 병목이 큰 구조가 됩니다. 그래서 이 프로젝트는 예매 흐름을 대기열, 좌석 선점, 비동기 확정 세 단계로 나눠 각 문제에 맞는 도구를 선택했습니다. 선택 기준은 익숙한 기술이 아니라, 순번 계산이 많은 문제인지, 짧은 임계 구간을 보호해야 하는 문제인지, 아니면 응답 경로에서 무거운 작업을 분리해야 하는 문제인지에 있었습니다.

Queue: Redis Sorted Set + SSE

대기열의 핵심은 저장이 아니라 순번 계산과 빠른 읽기였습니다. Redis Sorted Set은 score 기반 정렬 구조라 timestamp나 증가값을 기준으로 순서를 유지하기 쉽고, 특정 사용자의 위치와 전체 대기열 크기를 빠르게 계산할 수 있습니다. 상태 전파는 양방향 제어보다 서버에서 클라이언트로의 단방향 갱신이 중요했기 때문에 WebSocket보다 SSE를 우선 선택했습니다.

Seats: Redisson + State Transition

좌석 경쟁 구간은 매우 짧지만 실패 비용이 큰 임계 구간입니다. 애플리케이션 메모리 락은 인스턴스가 늘어날 때 안전하지 않다고 보고, Redis 기반 분산 락을 제공하는 Redisson을 사용했습니다. 좌석은 AVAILABLE, HOLD, SOLD 상태로 전이되며, 락은 상태를 바꾸는 직전 구간만 보호해 경쟁 범위를 좁혔습니다.

Booking: Kafka Async Flow

Kafka를 선택한 이유는 단순한 비동기화가 아니라, 생산과 소비의 시간 차를 허용해 응답 경로를 가볍게 만들기 위해서였습니다. producer는 요청을 빠르게 수신하고, consumer는 자체 속도로 확정 작업을 처리합니다. 이 방식은 즉시 완료성은 낮아지지만, 요청량 급증 시에도 사용자 응답과 내부 처리량을 분리해 볼 수 있다는 장점이 있습니다.

Observability: Prometheus + Grafana

대기열 제어, 좌석 락, 비동기 확정은 병목 위치가 서로 다르기 때문에 로그만으로는 흐름을 읽기 어려웠습니다. Prometheus는 시계열 지표 수집에 적합하고, Grafana는 이를 대시보드로 묶기 좋아 HTTP latency, Kafka lag, JVM, DB pool, queue 관련 지표를 같은 맥락에서 비교할 수 있게 했습니다.

Design

왜 이 구조가 필요했나

이 구조는 단순히 기술을 분리해 놓은 것이 아니라, 서로 다른 시간 특성을 가진 문제를 분리한 결과입니다. 대기열은 "많이 읽히는 문제", 좌석 선점은 "아주 짧게 강하게 잠가야 하는 문제", 예약 확정은 "사용자 응답과 처리 완료 시점을 분리해야 하는 문제"로 봤습니다.

왜 대기열이 먼저 필요했나

예매 오픈 순간에는 좌석 선택 로직보다 먼저, 너무 많은 사용자가 동시에 서비스 안으로 들어오는 문제가 발생합니다. 이 흐름을 그대로 애플리케이션과 DB에 전달하면 뒤 단계가 아무리 잘 짜여 있어도 병목이 쌓입니다. 그래서 진입량을 먼저 제한해 뒤 단계의 임계 구간으로 들어가는 요청 수 자체를 줄이도록 설계했습니다.

좌석은 왜 별도의 경쟁 구간인가

좌석 선택은 단순 조회가 아니라 경쟁 상태가 가장 집중되는 구간입니다. 중요한 것은 누가 빨리 눌렀는가보다 최종적으로 한 명만 점유되었는가였습니다. 즉, 이 문제의 본질은 목록 조회 성능이 아니라 AVAILABLE에서 HOLD로 바뀌는 순간의 원자성을 지키는 데 있었습니다.

예약 확정을 왜 분리했나

빠른 응답과 완전한 확정은 같은 타이밍에 일어날 필요가 없다고 판단했습니다. 사용자 요청이 들어온 순간 모든 확정 처리를 끝내는 구조는 응답 경로를 무겁게 만듭니다. 그래서 요청 수락과 최종 확정을 분리해, 프론트는 빠르게 응답하고 백엔드는 독립적인 소비 속도로 처리하게 했습니다.

무엇을 더 중요하게 봤나

좌석을 빨리 잡는 것보다, 잘못 잡힌 좌석을 오래 남기지 않는 것이 더 중요했습니다. 그래서 TTL 기반 만료와 상태 복구를 함께 설계했습니다. hold는 영구 상태가 아니라 짧은 유효 시간을 가진 임시 상태로 보고, 만료되면 복구 경로가 자동으로 작동하도록 두었습니다.

Code Evidence

설계는 코드에서 어떻게 드러났나

구조가 문서에만 있으면 의미가 없기 때문에, 각 책임이 실제 코드 단위로도 분리되도록 구성했습니다. 대기열 처리의 중심은 QueueService가 맡고, 좌석 상태 전이와 선점 해제는 SeatService가 담당합니다. 예약 요청은 BookingService에서 시작되지만, 실제 확정 흐름은 producer와 consumer로 나뉘어 동작합니다. 여기서 중요한 것은 서비스 이름보다, 어느 계층이 "판정"을 하고 어느 계층이 "상태 변경"을 담당하느냐입니다.

Queue QueueService

대기열 등록 자체보다 중요한 책임은 누가 지금 입장 가능한가를 판정하는 것입니다. 이 서비스는 순번 계산과 토큰 발급을 분리해, 진입 제어의 기준점을 만드는 역할을 합니다.

 Seats SeatService

좌석 서비스의 핵심은 좌석 조회가 아니라 상태 전이의 원자성을 지키는 것입니다. AVAILABLE에서 HOLD로 넘어가는 순간이 가장 민감한 경쟁 구간이므로, 이 지점을 보호하는 책임이 집중됩니다.

 Booking BookingService

예약 서비스는 모든 확정을 스스로 처리하지 않습니다. 어디까지를 동기 응답으로 남기고, 어디부터를 비동기 경로로 넘길지 경계를 정의하는 역할이 더 중요했습니다.

 Metrics Grafana Dashboard

지표는 단순한 운영 화면이 아니라 설계 가설을 검증하는 수단이었습니다. HTTP, Kafka, JVM, DB pool, queue 지표를 함께 보면 어느 계층에서 지연이 생기는지 분리해서 볼 수 있습니다.

Validation

무엇을 검증하려 했나

이 프로젝트의 목표는 기능 동작 여부보다, 경쟁 상황에서도 상태가 무너지지 않는지 확인하는 것이었습니다. 동시 좌석 선택 상황에서 중복 예약이 발생하지 않는지, 대기열이 진입량을 적절히 제어하는지, 예약 확정을 비동기화했을 때 사용자 응답과 내부 처리 흐름을 분리해 볼 수 있는지를 주요 검증 포인트로 삼았습니다. 수집한 수치는 단순한 성능 자랑이 아니라, 각 설계 선택이 실제로 어느 병목을 줄였는지 해석하기 위한 근거로 사용했습니다.

Retrospective

구현보다 더 중요했던 것은 경계 조건이었다

상태 전달 방식의 개선 여지

예약 확정 상태는 현재 polling 기반 조회가 남아 있습니다. 다음 단계에서는 SSE 또는 WebSocket 기반 상태 전파를 더 넓게 적용할 수 있습니다. 응답 경로를 가볍게 만든 대신, 최종 완료 상태를 사용자에게 어떻게 더 자연스럽게 전달할지는 아직 남아 있는 문제입니다.

운영 복잡도의 증가

Redis, Kafka, SSE, WebSocket을 함께 운영하는 만큼 로컬 검증에는 유리했지만 실제 운영 복잡도는 분명히 높아집니다. 기술을 분리할수록 각 계층의 책임은 명확해지지만, 장애 전파 경로와 관측 포인트는 오히려 더 많아집니다.

보상 흐름의 추가 설계

현재 결제는 mock 처리 기준입니다. 실제 운영 단계로 가려면 PG 연동, 멱등성, 실패 시 보상 트랜잭션까지 더 정교하게 다뤄야 합니다. 특히 "확정은 일부 성공했지만 후속 처리가 실패한 경우"를 어떻게 되돌릴지는 다음 단계의 핵심 과제입니다.
