GitHub README Architecture Performance

Real-time Queue Control / Seat Concurrency / Async Booking

실시간 티켓팅에서 대기열, 좌석 선점, 예약 확정 흐름을 분리 설계하고 검증한 프로젝트

이 프로젝트는 단순한 예매 CRUD가 아니라 동시 접속과 좌석 경합을 안전하게 처리하는 흐름을 만드는 데 집중했습니다. Redis 기반 대기열, Redisson과 DB 락을 이용한 좌석 선점, Kafka 기반 비동기 예약 확정, Prometheus와 Grafana를 이용한 운영 관측까지 하나의 흐름으로 정리했습니다.

Problem

왜 이 프로젝트가 어려운가

동시 접속

예매 오픈 시점에는 많은 사용자가 동시에 진입합니다. 모든 요청을 즉시 좌석 선택으로 보내면 서비스와 사용자 경험이 모두 무너집니다.

좌석 경합

같은 좌석을 여러 사용자가 동시에 선택하려고 해도 중복 예약 없이 한 명만 선점하도록 보장해야 합니다.

예약 확정 지연

예약 확정은 DB 쓰기와 후속 작업이 얽혀 있어 무겁습니다. API 응답 경로와 분리하지 않으면 병목이 커집니다.

상태 복구

좌석 hold 만료, 중간 실패, 상태 전파 누락 같은 경계 조건도 설계 단계에서 처리해야 합니다.

Architecture

핵심 설계 선택

Queue: Redis Sorted Set + SSE

대기 순서는 Redis Sorted Set으로 관리하고, 순번 갱신과 입장 가능 알림은 SSE로 전달했습니다.

Seats: Redisson + DB Lock

좌석 선점은 Redisson 분산 락과 DB 락을 함께 사용해 중복 점유를 막고, TTL 만료 후 자동 복구되도록 설계했습니다.

Booking: Kafka Async Flow

예약 요청은 빠르게 응답하고, 실제 확정은 Kafka consumer가 처리하도록 분리해 응답 경로의 부담을 줄였습니다.

Observability: Prometheus + Grafana

HTTP 지표, Kafka lag, JVM, HikariCP뿐 아니라 대기열 크기와 발급 토큰 수까지 운영 지표로 시각화했습니다.

Retrospective

한계와 다음 개선 포인트

Polling 기반 예약 상태 확인

예약 확정 상태는 현재 polling으로 조회합니다. 다음 단계에서는 SSE나 WebSocket 기반 상태 전파를 검토할 수 있습니다.

운영 복잡도 증가

Redis, Kafka, SSE, WebSocket을 함께 운영하는 만큼 로컬 검증에는 유리하지만 실제 운영 복잡도는 높아집니다.

PG 연동 미구현

현재 결제는 mock 처리입니다. 실제 PG 연동과 멱등성, 보상 트랜잭션까지 확장 검토가 필요합니다.
